# ORVIK Stall — Production Deployment

This repository is a Laravel 11 / PHP 8.2+ application with Vite assets. The included Dockerfile builds the frontend and PHP dependencies and serves Laravel through Apache with the document root set to `public/`.

The deployment configuration targets Railway and MySQL. It deliberately does **not** run database seeders.

## 1. Create the Railway project

1. Create a Railway account and a new project.
2. Add a **MySQL** database service.
3. Add a service from the GitHub repository `Hamz16-30/Orvik_Stall`.
4. Select the `deployment-prep` branch for this first deployment.
5. Railway detects the root `Dockerfile` and builds the application.
6. In the app service settings, generate a public domain.

Railway's MySQL service exposes `MYSQLHOST`, `MYSQLPORT`, `MYSQLUSER`, `MYSQLPASSWORD`, and `MYSQLDATABASE`. Configure the app service to reference the MySQL service's values (replace `MySQL` below with the exact database service name if you named it differently).

## 2. Set application variables

Set these variables on the **Laravel app service**:

| Variable | Value |
|---|---|
| `APP_NAME` | `ORVIK Stall` |
| `APP_ENV` | `production` |
| `APP_DEBUG` | `false` |
| `APP_KEY` | A newly generated Laravel key (see below) |
| `APP_URL` | `https://YOUR-RAILWAY-DOMAIN` |
| `LOG_LEVEL` | `warning` |
| `DB_CONNECTION` | `mysql` |
| `DB_HOST` | `${{MySQL.MYSQLHOST}}` |
| `DB_PORT` | `${{MySQL.MYSQLPORT}}` |
| `DB_DATABASE` | `${{MySQL.MYSQLDATABASE}}` |
| `DB_USERNAME` | `${{MySQL.MYSQLUSER}}` |
| `DB_PASSWORD` | `${{MySQL.MYSQLPASSWORD}}` |
| `SESSION_DRIVER` | `database` |
| `SESSION_SECURE_COOKIE` | `true` |
| `CACHE_STORE` | `file` |
| `QUEUE_CONNECTION` | `sync` |
| `FILESYSTEM_DISK` | `public` |

Generate a fresh key using the app container or a local copy of the project:

```bash
php artisan key:generate --show
```

Copy the generated value into Railway's `APP_KEY` variable. Do not use the sample key from `.env.example` or the test key in `phpunit.xml`. Never commit a real `.env` file or production secrets.

Set `APP_URL` to the HTTPS domain generated by Railway. If the domain changes later, update `APP_URL` and redeploy.

## 3. Persistent file storage

The app's public uploads use Laravel's `storage/app/public` directory. Attach a Railway volume to the Laravel app service at:

```
/var/www/html/storage
```

The startup script creates the required Laravel storage directories, fixes ownership, and refreshes the `public/storage` symlink. Without a persistent volume, uploaded files can be lost during container replacement or redeployment.

## 4. Database migrations and seeders

The included `railway.toml` runs:

```bash
php artisan migrate --force
```

as the pre-deploy command. Review migration changes before every production release and take a database backup before migrations that alter or remove existing data.

**Do not run `php artisan db:seed` or `php artisan migrate --seed` on production in the current repository.** `DatabaseSeeder` calls `DemoBusinessSeeder`, which creates sample businesses and privileged demo users with the password `password`. That is suitable only for isolated development/testing. Production should be initialized with a secure, individually created administrator account and production-safe seed data.

Before enabling public registration, initialize the required role/permission and plan/feature data once from the Railway app service shell:

```bash\nphp artisan db:seed --class=RolesAndPermissionsSeeder --force\nphp artisan db:seed --class=PlanAndFeatureSeeder --force\n```

These two seeders are separate from the demo seeder and establish the roles, permissions, plans, and default platform settings used by registration. Do not repeatedly run them after operators begin changing platform settings.

Create the first platform administrator deliberately using `php artisan tinker` in an interactive Railway shell. Create a `App\\Models\\User` with your own name/email, a unique strong password hashed with `Illuminate\\Support\\Facades\\Hash::make(...)`, `status => active`, and `is_platform_admin => true`. Do not use a sample/demo email or password. The normal public registration flow creates a business owner account, not a platform administrator.

## 5. Health check and deployment

- Health check path: `/up` (already registered in Laravel 11's `bootstrap/app.php`).
- The container listens on Railway's injected `PORT`.
- Apache serves only from Laravel's `public/` directory.
- Pushes to the connected branch can trigger Railway GitHub auto-deploys.

After deployment, test the public landing page, registration, login/logout, password reset email delivery, product creation, inventory, POS checkout, receipts, reports, file uploads, and tenant isolation.

## 6. Before inviting real businesses

- Configure a real mail provider and test password reset/invitation delivery.
- Confirm the platform administrator is created securely; never use the demo credentials.
- Configure database backups and test a restore.
- Verify persistent uploads and database retention.
- Review payment provider/webhook secrets and callback URLs before enabling paid subscriptions.
- Confirm timezone, currency, business registration, and legal pages.
- Add a custom domain later through Railway's domain settings and update `APP_URL`.

## 7. Notes

- PHP runtime: 8.3 (compatible with the project's `^8.2` requirement).
- Frontend: Node 20 build using `npm ci && npm run build`.
- Database: MySQL.
- Queue: synchronous until a dedicated worker is configured.
- Cache: file-based; suitable as an initial single-instance configuration, not a shared multi-instance cache.
- The first release is a deployment baseline, not a full production-readiness certification. Authentication, billing, mail, storage, backups, and tenant isolation still need end-to-end verification.
